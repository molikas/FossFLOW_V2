**Rig lessons.**
- **A synchronous infinite loop cannot be probed with a timeout** — jest's timeout never fires because the loop does not yield, and the worker hangs. ZIP-01 is observed by capping `Array.prototype.find` (the walk calls it once per step) and comparing a cyclic manifest against an acyclic control of the same size. Reusable for any "does this walk terminate?" question.
- **`expect(err).toBeInstanceOf(ProjectZipError)` FAILS even for a genuine one.** The app's `tsconfig.json` targets `es5`, so ts-jest downlevels `class extends Error` and the subclass prototype is lost; `.name` and `.code` survive. rsbuild configures no target/browserslist, so the shipped bundle does not downlevel this way — it is a probe artifact, not a product defect. Assert on `.code`/`.name`. (Same family as the S1 trap where a `jest.mock` dropped a class an `instanceof` depended on. Note `projectZip.readManifest` does its own `e instanceof ProjectZipError` re-throw guard, which is why the distinction matters.)
- **Baseline correction (thread S-f):** the harvested invariant claiming cross-diagram links live in Quill content HTML and in `headerLink` is **stale**. `modelItems.link` is the only schema field that can hold a diagram id — `textBox` has no link field and `headerLink` is a `z.string().max(2048)` URL. ZIP-02 is real for a different reason (out-of-scope refs), not for that one.

## Seed seams (2026-07-29 mapping — starting points, not a ceiling)

- readEntryString's zip-bomb guard reads JSZip's PRIVATE `_data.uncompressedSize` — a crafted zip can lie about the declared size, and a JSZip upgrade that changes the internal shape makes `declared` undefined, silently disabling the 50MB/entry cap either way
- importProject's folder remap: `folderRemap.get(f.parentId) ?? f.parentId` falls back to the REWRITTEN-but-never-created id when a parent is missing from the manifest — local provider accepts the dangling parentId (folder becomes invisible), Drive createFolder 404s and aborts mid-import with folders half-created
- App.tsx buildZipImportSummary reports manifest counts, while importProject silently `continue`s diagrams whose model is null — the success toast can overcount what actually imported
- replaceAll wipe is non-transactional: sequential deleteDiagram/deleteFolder over the network — one failure mid-wipe throws and leaves a half-destroyed workspace with nothing imported
- rewriteRefsInModel only rewrites values under keys literally named 'link' — any other embedded diagram-id reference in the model survives pointing at pre-rewrite ids that no longer exist after import
- Single-JSON import spreads the unvalidated blob straight into createDiagram (`{...blob, name, title}`) — a foreign file carrying folderId/deletedAt/id fields injects storage-level metadata (e.g., lands in a nonexistent folder and is invisible in the tree)
- Export from the Drive place writes lean models (icons stripped to imported-only) into the zip — round-trip fidelity depends entirely on requiredPacks surviving; a zip imported on a machine where pack fetch fails renders items with missing icons
- manifest.version missing/garbage produces the 'exported by a newer Axoview' message (SUPPORTED_VERSIONS has only '1') — misleading for merely corrupt manifests
- FileExplorer's ImportDialog imports into createTargetPlace (selected row's place, Drive-downgraded), App.tsx's direct path always imports to local root — same gesture, two different destinations depending on entry point

- **(technical-review-2026-07-29 §3 finding 2 / known_issues (runtime import cycle))** The Axoview → UiOverlay → ExportImageDialog → Axoview value cycle is safe ONLY while every binding is referenced lazily inside function bodies; a module-eval-time read becomes a TDZ crash at import. → *Add a module-level const in ExportImageDialog that touches an Axoview export (a default prop, a decorator, a memoized style derived from the component): the app crashes at boot with a stack pointing at an innocent consumer. ## Product questions (SUSPECT verdicts)

- **ZIP-09 — should the import destination depend on which surface you launched Import from, and on whether the tree happens to be empty?** As built there are THREE entry points into one operation. (1) The toolbar Import with an *empty* tree opens a bare file input: no destination choice, a hard-coded `{ kind: 'root' }`, and a toast that names counts. (2) The same toolbar Import with a *non-empty* tree opens `ImportDialog` over `storage` — the manager, so whichever place the open diagram put it in — offering root / newFolder / **replaceAll** and a generic "Import complete". (3) The file explorer opens the same dialog over `providerFor(createTargetPlace)`, the *selected row's* place, which can differ from (2)'s. Two consequences worth a decision: the same button is destructive-capable (replaceAll) or not depending on tree emptiness, and (2) vs (3) can land the same archive in different places with nothing on screen naming the destination. **Recommendation:** always open `ImportDialog` (an empty tree is not a reason to remove the destination choice — it is a reason to preselect root), show the resolved destination place in the dialog, and pass the place explicitly rather than letting one path read the active provider and the other the selected row. That also gives the count-bearing toast one home. Note the seed seam's claim that "App.tsx's direct path always imports to local root" is wrong — it follows the active place.

> **CLOSED 2026-07-30 — owner decisions** ([DECISIONS.md](../DECISIONS.md)): ZIP-09 — one import flow: every entry point opens ImportDialog, empty tree preselects root, destination place named on screen and passed explicitly.
