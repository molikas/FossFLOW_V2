# S3 — Drive-native sharing & readonly preview ladder

**Status:** DONE · **Counted hypotheses:** 15 / 10 · **Bugs:** 10 · **Suspects:** 1 · **Hypothesis ID prefix:** `DRV-`

**Scope:** Drive-place sharing is ACL management over Drive REST v3 permissions (driveSharing.ts: list with page drain, add person, anyone-with-link toggle, remove; DriveShareError carries Google's machine reason for policy-empty messages) plus a deterministic live preview URL /display/drive/<fileId>. The readonly viewer resolves via a ladder (drivePublicRead.ts): rung 1 anonymous server proxy /api/public/drive/:fileId (worker-only, honors trashed→410, 60s browser cache), rung 2 drive.file token read, then typed failures (needs-signin / needs-grant / not-found / transient) rendered by DriveDisplayGate — sign-in with one-shot auto-retry, Picker per-file grant (drivePicker.ts, deep-targeted DocsView), switch-account recovery. AppToolbar splits Share: session-place snapshot popover (StorageManager.shareDiagram → /display/p/<uuid>) vs Drive caret menu (copy link + ACL overview + Manage dialog). DiagramLifecycleProvider hosts the three mutually-exclusive display loaders.

## Seed seams (2026-07-29 mapping — starting points, not a ceiling)

- Ladder misclassification of public-file failures: rung-1 proxy 404 ('not-public') falls through to the token rung — a signed-out viewer of a genuinely public file that transiently 404s upstream gets the needs-signin wall (sign-in can't help); conversely proxy 413 too-large maps to terminal 'not-found' and renders the generic ReadonlyLoadErrorDialog with wrong copy.
- afterGrant stickiness: driveAfterGrantRef flips true after one Picker pick; if the grant registers slowly (Drive propagation) the retry's 403/404 now maps to terminal 'not-found' instead of needs-grant — recipient hits a dead end for a file they were just granted; check whether the ref ever resets on subsequent manual retries/navigation.
- Picker silent-fail trap: setAppId takes the project NUMBER — wrong value makes picks 'succeed' with no grant (documented trap); plus a PICKED whose docs array omits the target resolves 'cancelled' with zero user feedback (gate silently stays up).
- setAnyoneWithLink(false) deletes anyone-permissions serially; a mid-loop failure leaves the file still link-readable while the select shows the attempted 'restricted' until refresh — and the worker proxy's Cache-Control:60s means revocation lags up to a minute in a viewer's browser anyway (revocation latency seam).
- AppToolbar quick-copy heuristic: when the ACL overview fetch failed (driveOverview null) it shows the SUCCESS toast ('don't cry wolf') — copying a restricted link with a confident success message; DriveShareManageDialog.handleCopy has the inverse behavior (warns). Inconsistent truthfulness between the two copy paths.
- Readonly enforcement is route/UI-level only: /display/drive and /display/p load into the same canvas via applyLoadedDiagram — verify no save/autosave path is reachable in readonly (an autosave firing on the Drive display route would write with the RECIPIENT's token to the owner's file id, or 403). Also the recipient's canvas id is set to shareUuid/fileId — any code keying storage ops off currentDiagram.id is a seam.
- Stale-response guards: AppToolbar's shareReqRef monotonic id must invalidate late getAccessOverview/shareDiagram resolutions across diagram switches; DiagramLifecycleProvider's cancelled-flag pattern covers navigation — probe rapid open/close/switch sequences for late-paint of the wrong diagram's share state.
- Session-place share popover error contract: LocalStorageProvider.shareDiagram throws bare 'Share failed: <status>' — ADR 0011 requires dialog treatment; share-error.spec.ts covers the 500 path, but backend 404 (diagram deleted between open and share) and timeout (AbortSignal 10s) paths are less covered.
- DriveShareManageDialog runAction serialization: one busy flag serializes writes, but Enter-key handleAdd runs runAction then addRecentShareEmail/setAddEmail even on failure — the email field clears after a FAILED add, forcing retyping (check runAction swallow: it catches and sets actionError, so handleAdd's post-steps always run).
- (mapper note) Largely probe-able WITHOUT live Google via Playwright route interception — established patterns: drive-display.spec.ts fulfills **/api/config (drivePublicPreview toggle), **/api/public/drive/**, and https://www.googleapis.com/drive/v3/files/** with CORS headers; share-error.spec.ts mocks the session share endpoint. The permissions API (driveSharing.ts) and DriveShareManageDialog can be driven the same way IF the auth store is primed (needs a stubbed GIS bridge or component tests — jsdom tests exist for the dialog). Needs LIVE auth: Picker grant flow end-to-end, Workspace policy rejections (publishOutNotPermitted), Drive grant-propagation timing, real notification emails, resourceKey-bearing legacy files.

- **(ADR 0034 round-2 (normalizeQuillHtmlSpaces))** &nbsp;-serialized spaces are converted to real spaces on commit AND on load, so fixed-width boxes wrap; auto boxes render `pre`, fixed boxes `pre-wrap`. → *A read-only path that loads content without the editor-load normalization — the /display/drive viewer or a share-snapshot render — shows a legacy &nbsp;-heavy fixed-width box as one unbreakable line overflowing the box. Load normalization lives in the editing load chokepoint; no test loads legacy content through the read-only display routes.*
- **(ADR 0037 §2 (active provider follows open diagram))** Switching the open diagram to another place flushes the pending autosave to the OLD place before setting the new active provider. → *With a dirty session diagram (debounced autosave pending), immediately open a Drive diagram: if the flush is fire-and-forget rather than awaited before the provider swap, the session autosave either writes through the Drive provider (wrong place) or is cancelled (silent data loss). driveTransfer/authStore tests don't cover the open-diagram provider-swap flush ordering.*

The cheap fix (invalidate on zero-listing or 404) is catalogued but unimplemented — any test asserting 'save succeeded ⇒ durable' is false here.*
- **(ADR 0011 §1 (error UX contract))** Every failure-of-intent (user clicked/typed/dragged) surfaces an explicit Dialog; notification-toast-only handling and silent .catch(() => {}) are forbidden for such paths. → *Click 'Copy share link' in a context where navigator.clipboard.writeText rejects (non-secure context, permissions policy): the catalogued S1–S20 silent surfaces are still open, and new Drive-share paths added since B-9a (copy preview link, Manage-access actions) have never been audited — a rejection likely dies in a toast or a swallowed catch, and no test asserts dialog-vs-toast classification for new surfaces.*
- **(canvas-interaction.md §5.9 checklist item 5 (Label preview channel))** Canvas-drawn elements publish a live drag preview channel (labelMove/labelMoves) that must be cleared on BOTH mouseup (after commit) and exit (escaped drag). → *Abort a group drag containing Labels via a mid-drag tool hotkey (DragItems.exit path): if clearLabelMoves runs only in the mouseup handler, the stale labelMoves map keeps painting Labels at the aborted offset while the model has them at origin — 'the element jumps when I next touch it'. - **(ADR 0042 §2 + worker app.ts (resourceKey fix))** The public Drive read-proxy validates fileId and (since 2026-07-29) resourceKey on the allowlist /^[A-Za-z0-9_-]{10,120}$/, with a malformed resourceKey DROPPED so 'no valid request regresses'. → *Google resource keys can be shorter than 10 chars or contain other legal characters — a legitimate short resourceKey now gets silently dropped, so an 'anyone with the link' file that REQUIRES the key returns 404 from Drive and the viewer hits the auth-gate ladder with no hint. The worker test verifies the drop behavior, not that real-world resourceKey formats pass the same regex as fileIds.*

## Product questions (SUSPECT verdicts)

**DRV-05 — how should a partially-failed link revocation be reported?**

`setAnyoneWithLink(fileId, false)` lists the file's `type:'anyone'` permissions and
deletes them one at a time. Measured with two such permissions and the second DELETE
failing 500: the first is gone, the second is not, nothing rolls back, and the caller
receives a `DriveShareError` that says only that the operation failed. `runAction` in
`DriveShareManageDialog` skips its `refresh()` on a throw (`listPermissions` called
once), so the list the user is looking at is the pre-delete one — the file is still
link-readable and nothing on screen says so.

The reachability of the damaging case is the honest open question: Drive normally
carries at most one `anyone` entry per file, so the loop usually has one iteration and
a failure leaves state genuinely unchanged, which the current error is an adequate
report of. Nothing in ADR 0042 says what a multi-entry partial revocation should do.

**Recommendation:** cheap and strictly better either way — `refresh()` in
`runAction`'s `catch` as well as its success path, so the ACL the user sees after any
failure is the ACL that exists; and have `setAnyoneWithLink(false)` collect per-permission
outcomes and report "still shared" rather than a bare throw when at least one delete
survived. Owner call on whether the multi-entry case justifies more than the refresh.
